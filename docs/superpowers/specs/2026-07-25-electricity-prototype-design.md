# Прототип учёта электричества для дачи

## Цель

Создать мобильный веб-прототип для Android, в котором пользователь может сохранять показания двухтарифного счётчика, рассчитывать начисления по разным тарифам Т1 и Т2, видеть историю и отмечать оплату. Приложение размещается отдельно от существующих страниц репозитория по адресу `/electricity/`.

## Пользовательский сценарий

1. Пользователь регистрируется или входит по email и паролю.
2. На вкладке «Новая запись» он вводит дату, текущие показания Т1 и Т2 и соответствующие тарифы.
3. Первая запись становится начальной точкой и не создаёт начисление.
4. Для следующих записей приложение показывает предварительный расчёт до сохранения.
5. На вкладке «История» пользователь видит задолженность и записи от новых к старым.
6. Запись можно отредактировать, удалить после подтверждения или отметить оплаченной.

## Интерфейс

Приложение использует светлый мобильный интерфейс, рассчитанный прежде всего на экран Android. После входа доступны две вкладки в нижней навигации:

- «Новая запись»: дата, показания Т1/Т2, тарифы Т1/Т2, расход и предварительный итог;
- «История»: общая неоплаченная сумма и карточки периодов.

Карточка истории показывает дату, показания, расход, тариф и стоимость отдельно для Т1 и Т2, общую сумму и статус оплаты. Пустое состояние поясняет, что первая запись будет стартовой и не создаст начисление.

Экран авторизации объединяет регистрацию и вход. Введённые в форму значения сохраняются при сетевой ошибке, чтобы пользователь мог повторить отправку.

## Расчёты

Записи сортируются по дате по возрастанию. Для каждой записи после первой:

```text
расход Т1 = текущий Т1 − предыдущий Т1
расход Т2 = текущий Т2 − предыдущий Т2
стоимость Т1 = расход Т1 × тариф Т1
стоимость Т2 = расход Т2 × тариф Т2
итого = стоимость Т1 + стоимость Т2
```

Денежные суммы отображаются в рублях с двумя знаками после запятой. Тариф каждой записи применяется к расходу периода, который заканчивается этой записью.

Первая хронологическая запись всегда является стартовой: её расход и стоимость равны нулю. Изменение даты, показаний или удаление старой записи приводит к пересчёту всех последующих периодов и общей задолженности.

## Проверки данных

- дата обязательна;
- показания Т1 и Т2 — неотрицательные числа;
- тарифы Т1 и Т2 — положительные числа;
- на одну дату разрешена одна запись пользователя;
- показания не могут быть меньше предыдущей записи;
- при вставке или редактировании старой записи её показания не могут быть больше следующей записи.

Ошибки показываются рядом с соответствующим полем и не очищают форму.

## Архитектура

Клиент остаётся статическим приложением на HTML, CSS и JavaScript с отдельными модулями для:

- авторизации и сессии;
- доступа к данным;
- чистых функций расчёта и валидации;
- состояния интерфейса;
- отображения формы, истории и уведомлений.

Supabase предоставляет:

- регистрацию и вход по email и паролю;
- PostgreSQL для синхронизации записей между устройствами;
- восстановление сессии после повторного открытия;
- Row Level Security, ограничивающий доступ пользователя только его данными.

Статические файлы приложения публикуются через существующий GitHub Pages workflow в каталоге `/electricity/`. URL проекта Supabase и публичный `anon`-ключ задаются в клиентской конфигурации. Этот ключ допустим в браузере только вместе с включёнными политиками Row Level Security; сервисный ключ в репозиторий не добавляется.

## Модель данных

Таблица `electricity_readings`:

- `id` — UUID, первичный ключ;
- `user_id` — UUID пользователя Supabase Auth;
- `reading_date` — дата показаний;
- `t1_reading` — показание Т1;
- `t2_reading` — показание Т2;
- `t1_rate` — тариф Т1;
- `t2_rate` — тариф Т2;
- `is_paid` — статус оплаты;
- `created_at` и `updated_at` — служебные временные метки.

Уникальное ограничение `(user_id, reading_date)` не допускает две записи на одну дату. Политики `SELECT`, `INSERT`, `UPDATE` и `DELETE` проверяют `auth.uid() = user_id`.

Расходы и суммы не сохраняются как отдельные поля: клиент вычисляет их из последовательности показаний. Это исключает устаревшие суммы после редактирования или удаления старой записи.

## Поток данных

После восстановления сессии клиент загружает все записи пользователя, сортирует их по дате и вычисляет производные значения. Сохранение, редактирование, удаление или изменение статуса отправляется в Supabase; после успешного ответа локальное состояние обновляется и расчёты выполняются заново.

При выходе данные текущего пользователя удаляются из памяти интерфейса. После входа на другом устройстве история загружается из той же облачной базы.

## Ошибки и состояния

- во время входа и загрузки показывается индикатор;
- сообщения Supabase преобразуются в понятные русские тексты;
- при потере сети пользователь видит уведомление и может повторить действие;
- неуспешное сохранение не добавляет фиктивную запись в историю;
- удаление требует подтверждения;
- истёкшая сессия возвращает пользователя на экран входа.

## Тестирование

Автоматические тесты покрывают:

- стартовую запись без начисления;
- расчёт Т1, Т2 и общей суммы;
- разные тарифы Т1 и Т2;
- пересчёт после изменения последовательности;
- сумму неоплаченных записей;
- неубывающие показания и граничные значения.

Ручная проверка в мобильном размере покрывает регистрацию, вход, создание стартовой и следующей записи, предварительный расчёт, историю, статус оплаты, редактирование, удаление и сообщения об ошибках.

## Вне первой версии

- нативный APK;
- другие коммунальные услуги;
- совместный доступ нескольких пользователей к одному объекту;
- экспорт в Excel или PDF;
- напоминания и push-уведомления;
- автоматическая установка тарифов по региону.
